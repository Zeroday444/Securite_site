Comment ce site est protégé

Page d'apprentissage, à retirer avant une mise en ligne. Pour chaque protection : le risque, où lire le code, et comment constater qu'elle fonctionne.

Idée à retenir : tout ce qui vient du navigateur peut avoir été modifié (formulaire, cookie, adresse). Le serveur revérifie donc tout lui-même.

Les comptes de test (un admin, deux clients) sont créés dans db.js.

1. Seul le dossier public/ est accessible

Risque : qu'un visiteur télécharge le code du serveur ou le fichier de la base.

Code : serveur.js, ligne express.static.

Vérifier : ouvre /serveur.js ou /data/boulangerie.db dans le navigateur : introuvable.

2. Validation côté serveur (contact)

Risque : les required du HTML se contournent, on peut envoyer n'importe quoi au serveur sans passer par la page.

Code : routes.js, route /api/contact.

Vérifier : dans les outils du navigateur (F12), retire l'attribut required d'un champ puis envoie le formulaire vide : le serveur refuse quand même.

3. Le texte des visiteurs est affiché comme du texte

Risque : si un message contenant des balises HTML était inséré tel quel dans la page des messages, le navigateur de la boulangerie l'interpréterait (faille dite XSS).

Code : echapperHtml dans outils.js, utilisée dans la route /admin/messages. Côté navigateur, on utilise textContent et jamais innerHTML.

Vérifier : envoie un message contenant <b>bonjour</b>, puis connecte-toi en admin et ouvre les messages : les balises s'affichent telles quelles, le texte n'est pas en gras.

4. Anti-spam

Risque : des robots qui remplissent le formulaire en boucle.

Code : champ piège site_web dans contact.html, et limiteContact dans routes.js.

Vérifier : envoie quatre messages de suite : le quatrième est refusé pendant dix minutes.

5. Mots de passe hachés

Risque : si la base fuit un jour, tous les mots de passe des clients avec, et beaucoup de gens réutilisent le même partout.

Code : hacherMotDePasse et verifierMotDePasse dans outils.js.

Vérifier : lance npm run voir-db : la colonne hash ne permet pas de retrouver les mots de passe.

6. Requêtes SQL préparées

Risque : si on fabriquait une requête en collant du texte tapé par le visiteur, il pourrait y glisser du SQL et lire ou modifier la base (injection SQL).

Code : partout dans routes.js, les valeurs passent par des ? remplis par la base.

Vérifier : essaie de te connecter avec une apostrophe dans l'email : simple « email ou mot de passe incorrect », aucune erreur technique.

7. Session côté serveur, cookie protégé

Risque : qu'on se fasse passer pour un autre client en modifiant ou en volant son cookie.

Code : ouvrirSession et cookieSession dans routes.js.

Vérifier : connecte-toi, F12, onglet Application puis Cookies : sid est une longue valeur aléatoire, marquée HttpOnly. Tape document.cookie dans la console : il n'apparaît pas.

8. Tentatives de connexion limitées

Risque : deviner un mot de passe en en essayant des milliers, ou découvrir quels emails sont inscrits.

Code : limiteConnexion et le message unique dans la route /api/connexion.

Vérifier : trompe-toi six fois de mot de passe : le compte est bloqué un quart d'heure. Le message est le même pour un email inconnu.

9. Le prix est calculé par le serveur

Risque : si le serveur faisait confiance au prix envoyé par la page, un client pourrait le changer avant de commander.

Code : route POST /api/commandes dans routes.js, et boutique.js qui n'envoie que les identifiants et les quantités.

Vérifier : F12, onglet Réseau, passe une commande et regarde ce qui est envoyé : aucun prix.

10. Chacun ne voit que ses commandes

Risque : lire la commande d'un autre client en changeant le numéro dans l'adresse.

Code : route /api/commandes/:id, la condition AND user_id = ?. Même principe pour /admin/messages, réservée au rôle admin.

Vérifier : connecté avec un compte client, ouvre /api/commandes/1 puis /api/commandes/2 : une seule des deux s'affiche. Ouvre /admin/messages : refusé.

11. En-têtes de sécurité et requêtes venant d'autres sites

Risque : un script étranger exécuté dans la page, ou un autre site qui ferait agir le navigateur d'un client connecté à sa place (CSRF).

Code : en-têtes dans serveur.js, contrôle de l'origine au début de routes.js, SameSite sur le cookie.

Vérifier : F12, onglet Réseau, clique sur une page et regarde ses en-têtes de réponse.

Ce qu'il resterait à faire avant une vraie mise en ligne

  • HTTPS obligatoire (certificat fourni par l'hébergeur), avec NODE_ENV=production pour activer le cookie Secure.
  • Paiement : confié à un prestataire (Stripe, PayPlug, SumUp…). Le site ne voit jamais de numéro de carte.
  • Email de confirmation à l'inscription et « mot de passe oublié » par lien à usage unique.
  • RGPD : mentions légales, politique de confidentialité, durée de conservation, suppression sur demande.
  • Secrets (clés, mots de passe d'email) dans un fichier .env jamais publié.
  • Sessions et limites enregistrées en base : ici elles sont en mémoire et s'effacent au redémarrage.
  • Mises à jour régulières (npm audit) et sauvegardes de la base.
  • Supprimer les comptes de test et cette page.
